# Data Plan

## Context provenance
- `给我生成一个类似于libtv 无限画布视频生成工具核心功能一定要在` (verbatim user request; defines the whole scope: a LibTV-style infinite-canvas video creation tool with the core features present)
- No other external context applied; node/workflow design follows the well-known LibTV pattern (infinite canvas + node workflow: 提示词 → 文生图/图生图 → 视频合成 → 导出) as the user explicitly named that product as the reference.

## Tested sources
### ctx.tool.generate_media (server action image generation)
**Used by**: `generateImage` action — turns a prompt node into a real AI-generated image stored in ctx.blobs, returned as a durable own-origin URL + blobKey persisted on the node.
**Test command**: `grep -n generate_media node_modules/@hatch/space-sdk/dist/verticals.d.ts` plus reading the `SpaceToolClient` interface (lines 268–345).
**Sample output**: `generate_media(prompt: string, options?: { orientation?: "square"|"landscape"|"portrait", key?: string }): Promise<GeneratedMedia>` where `GeneratedMedia = { blobKey, url, contentType, bytes }`, url is a stable own-origin `./blobs/<key>` URL.
**Processing**: prompt assembled client-side from the node's own prompt text plus any connected upstream text nodes and style suffix; orientation mapped from the node's aspect setting (16:9→landscape, 9:16→portrait, 1:1→square). Result blobKey + url saved onto the image node; failures surface as a node-level error state, never a fake image.
**Probe note**: `bun probe-ctx.js` reports `ctx.tool.generate_media is not available in probe mode — requires a built web artifact`, so the capability is verified from the shipped SDK type contract and will be exercised end-to-end in the audit against the built artifact.

### Video synthesis (client-side, no external source)
**Used by**: the 合成视频 (compose) flow on video nodes.
**Mechanism**: the browser draws the node's connected keyframe images onto an offscreen canvas at the chosen resolution (720p/1080p per aspect), animating per-shot Ken Burns pan/zoom and crossfades on the shot durations, captures `canvas.captureStream(30)` into a `MediaRecorder` (video/webm), and produces a real playable/downloadable video file. The file is uploaded via the `saveVideo` action (base64 → ctx.blobs) so the video node persists and replays after reload. No simulated progress-only 'generation': if MediaRecorder is unsupported the UI says so honestly.
**Checked with**: standard Web APIs (CanvasRenderingContext2D, captureStream, MediaRecorder) — no network source involved.

## Imagery
Imagery not needed at build time: every image in the artifact is either generated at runtime by the user's own generate action (stored in ctx.blobs) or uploaded by the user. No stock or decorative photos are used; node/empty states are drawn with CSS/SVG.

### Platform-token generation alignment (edit, 2026-11-10)
User asked: 「操作功能全部一一对齐，生图，生视频，生文都用你自己的token」 — all generation must run on Muse's own platform models (no external API key anywhere), and canvas operations aligned 1:1 with the LibTV pattern.
- **生文 (text)** — `generateText` action via `ctx.inference.complete` (schema `z.string()`), modes: expand（扩写提示词）/ script（短视频脚本）/ storyboard（分镜脚本， strict line format 镜头N｜时长｜运镜｜画面｜字幕， parsed client-side by `parseStoryboard` back into shot nodes) / captions（标题文案）. `enhancePrompt` kept for compatibility; the UI now uses `generateText`.
- **生图 (image)** — unchanged: `generateImage` via `ctx.tool.generate_media`.
- **图生图 (image-to-image)** — `varyImage` action: client re-encodes the source blob to JPEG base64 (vision accepts JPEG/PNG only), `ctx.inference.complete` with `images:` rewrites it per the user's instruction, then `ctx.tool.generate_media` renders the variation; result becomes a new node wired from the source and a history row.
- **生视频 (video)** — the platform exposes NO text-to-video model (checked `SpaceToolClient`: only `generate_media` for images + `inference`). The honest full pipeline on platform tokens: `planShots` action (`ctx.inference` structured output: prompt/caption/duration/motion per shot) → `generateImage` per shot (frames also land on the canvas as real wired shot nodes) → existing client-side `composeVideo` synthesis → `saveVideo`. The pre-existing image-to-video compose path （连接分镜图→合成） is unchanged. No external video API, no simulated generation.
- **Operations parity added**: multi-select (Shift+click toggle, Shift+drag marquee, group drag), copy/cut/paste/duplicate-in-place (Ctrl+C/X/V/D), select-all, undo/redo (debounced structural snapshots, nodes+edges only), Delete/Esc/Ctrl+S/F shortcuts + help panel, canvas & node right-click context menus, align (6 modes) + distribute + topological auto-layout （整理）, node lock, double-click title rename, clickable minimap jump, Run-all pipeline （运行全部）, one-click storyboard split （分镜脚本→镜头节点→成片节点）.

### Real image-to-video pipeline (edit, 2026-11-10)
User complaint: composed videos felt like a PPT — storyboard stills stitched with Ken Burns + crossfade. Asked for storyboard image + prompt → continuous video （图生视频）, not image stitching.
- **Platform check (re-verified this edit)**: `SpaceToolClient` in the shipped SDK exposes `generate_media` for IMAGES only (orientation + key options; returns image blob) plus `ctx.inference` — there is still NO text-to-video / image-to-video model reachable from a server action. So the pipeline below is the genuine image-to-video route on platform tokens; the UI copy says exactly what it does （逐帧生成 + 光流插帧）, never claims a video model.
- **图生视频帧 (frame chaining)** — new `animateFrame` action: client sends the current frame (JPEG base64) + the shot's prompt + camera motion; `ctx.inference.complete` WITH the image writes the next frame's prompt (same subject/scene/composition/palette, action and camera advanced one small step); `ctx.tool.generate_media` renders it; stored as a blob + a `generations` history row (`图生视频帧 N：…`). Client chains ~1 frame per second of shot duration (2–4 per shot), each from the previous frame, and persists the sequence on the image node (`frames: string[]` in the graph JSON). Sequences are reused on re-compose; regenerating/replacing the still clears them.
- **Entry points**: image node button「图生视频：生成连续帧」; video node「图生视频合成」auto-animates every connected shot first; 文生视频 pipeline animates its planned shots too; one frame-by-frame stage line （图生视频：镜头 i/N 生成连续帧 j/M…) is shown while it runs.
- **Synthesis v2 (`compose.ts`)**: replaces slideshow crossfades with optical-flow interpolation — block-matching flow (176px analysis copy, forward+backward with consistency check + smoothing) between every consecutive frame pair, mesh-warp in-between synthesis at 30fps, continuous smootherstep camera, temporal ghost smoothing within a shot, captions, MediaRecorder → WebM/MP4 via the existing `saveVideo` action. Shot boundaries share the frame spacing so motion morphs across cuts.

No page surface offers or describes still-image synthesis （推拉/淡入淡出/光流插帧/逐帧生成） anymore. The earlier "Real image-to-video pipeline" section above is superseded by this one.
- **Kept intact**: text generation (`generateText` incl. storyboard split — now writes the shot's caption into a dedicated `caption` field instead of embedding 字幕 in the prompt text), image generation (`generateImage`), image-to-image (`varyImage`), projects, canvas ops, history.

- **Video nodes are now 分镜包 (storyboard package) nodes**: they collect wired image nodes in edge order and show the ordered shot list (thumbnail, title, duration) + shot count + total duration + the 6-per-round note; they keep upload/playback/download so the finished film Muse returns in chat can be attached back. No synthesis controls.

Shots are chunked into rounds of ≤6 with a batch picker. Per round the user can: ① download each shot image (`shot-NN.<ext>` via fetch of its blob URL), ② download a manifest JSON (`<项目>-分镜清单-第N批.json`: per shot — index, title, image_file, image_prompt (effective prompt incl. upstream text), motion_prompt, caption, duration_seconds, camera_motion label, aspect — plus a note telling the receiver to generate one real-motion clip per shot and cut in index order), ③ copy a ready-to-paste Chinese handoff text for chat (also shown in a read-only textarea). The drawer states the division of labor plainly: tool does storyboards, Muse generates true-motion clips chat-side on Muse's own token, max 6 shots per round.

### Film save-back root-cause fix: delivery encode first, bounded attempts, immediate failure (edit, 2026-11-10)
User: 「直接发我成片，并且修改工具，不让它再次出现」 — about the save-back step, which had now failed three different ways across three real runs: request 1 barely saved; request 2 rendered its film but never saved it and was eventually killed by the stall timeout; project 3's task spent 8+ minutes re-encoding the finished film smaller and smaller (12MB→4.4MB→2MB→…→0.59MB), retrying `saveFilmToProject` with each version, reporting NO progress meanwhile — so the page false-alarmed "可能卡住了" while the film sat finished at 「正在保存成片」.
- **Root cause**: `saveFilmToProject` takes the whole MP4 as ONE base64 action argument, and nothing told the background task what size was acceptable or required it to report during saving. The task therefore had to discover the practical limit by blind trial, silently.
- **Chunked/resumable upload — investigated, NOT possible on this surface**: `BlobClient` in the shipped SDK exposes only `put/getUrl/head/list/delete` — there is no way to READ blob bytes back server-side, so uploaded chunks could never be reassembled into one playable file. Per the approved fallback, the single-call channel is hardened at both ends instead (below).
- **Delivery-encode-first contract (both spawn briefs, `requestFilm` + `spawnAgentFilm`)**: before ANY save attempt the task must produce a delivery encode — 720p at the film's aspect, bitrate scaled to the film's duration so the file lands ≤ ~1.5MB — and save THAT; the full-resolution master stays local for direct chat delivery and is never sent to the tool. Before EVERY save attempt it reports the save stage WITH the attempt number （正在保存成片（第 N 次尝试）) on the film channel (and the agent channel for Agent runs); at most 3 attempts total; a too-big error means re-encode ONCE straight to the ≤1.5MB target — never a ladder of shrinking sizes.
- **Server hard cap with an immediate, explicit error**: `saveFilmToProject` now estimates the decoded size from the base64 length BEFORE decoding and rejects anything over `FILM_SAVE_MAX_BYTES` (8MB) with an error naming the cap and the required delivery target （720p、1.5MB 以内）, so a task that still sends something too big learns the exact target on its first attempt.
- **Lenient saving-stage stall model**: `filmStallState` now takes `progressStage`; when the stage is the saving stage （包含「保存」), the no-progress thresholds are 10 min warn / 30 min auto-fail instead of 5/15 (45-min hard cap unchanged), and every attempt report resets the clock via `updatedAt`. The client's two local stall computations mirror the 10-min saving warn threshold, and the stalled-banner auto-end copy is stage-aware (30 vs 15 minutes). A normal, reported save retry can no longer false-alarm.
- **Immediate honest failure — new `failFilmSave` action** (requestId, reason): the briefs require the task to call it the moment saving has definitively failed (after the bounded attempts). It flips the film request AND any linked agent run to `failed` immediately — no hanging in `running` until a timeout — with a plain-language error that also records the fallback fact: 「成片文件已在后台生成完毕，可由 Muse 直接在对话里发给你，不用重新生成」. The saving-stage auto-fail reason carries the same note.
- **Verified in sandbox** (on the copy of the actually-stuck project 3, request 4 at 正在保存成片 8/8): a `reportFilmProgress` with stage 「正在保存成片（第 2 次尝试）」 landed and reset `updated_at`; `failFilmSave` flipped BOTH the film request and agent run 1 to failed instantly with the reason + chat-delivery note; a normal small `saveFilmToProject` still saves end-to-end. The oversize-rejection branch is a pre-decode length check, verified by code inspection (an >11M-char test argument isn't practical to pass through the action test harness).
- Not regressed: stall self-heal for non-saving stages, media-preservation merge, response-level node-media backfill, agent build flow.

## Long-term data behavior
- **Refresh policy**: none — all data is user-created project state; no external feed and no scheduled refresh.
- **Growth**: projects → canvases (JSON node/edge graph) → generation history rows; assets live as blobs keyed per project/node. Deleting a project removes its rows and blobs.
- **Ordering**: projects and history newest-first; canvas graph order is spatial, stored as authored.
- **Time semantics**: created_at/updated_at are creation instants rendered viewer-local; shot durations are plain seconds chosen by the user.

## Rejected approaches
- **Tried**: probing `ctx.tool.generate_media` via probe-ctx for a live sample.
  **Why rejected**: the runner explicitly refuses generate_media in probe mode; relying on the SDK's shipped type contract instead and verifying in the built-artifact audit.
- **Tried**: server-side text-to-video generation.
  **Why rejected**: the Space tool surface exposes image generation only; no video model is reachable from an action. Video is therefore genuinely synthesized in the browser from generated keyframes (real WebM output) rather than faked with a mock 'AI video' result.
- **Tried**: storing uploaded/generated media as base64 in DB rows.
  **Why rejected**: binary belongs in ctx.blobs; DB keeps only blob keys and metadata.

### Automatic film generation, no export (edit, 2026-11-10)
User's latest instruction: 「工具里面不要导出分镜包交给你，你直接自己生成保存后直接合成」 — the manual export/hand-off step is rejected for good; the tool itself must trigger the whole thing.
- **Export flow fully removed**: top-bar 导出分镜包交给我 button, per-node export button, node context-menu export entry, and the entire export drawer (per-round shot downloads `shot-NN.*`, manifest JSON download, copyable handoff text, batch picker, 6-per-round batching) are deleted from the client. No page surface mentions exporting, handing off, or sending files to Muse.
- **New one-click flow**: top-bar and per-成片-node button「生成并合成成片」 (plus node context menu). The client first flushes the canvas via `saveProject`, then calls the new `requestFilm` action. While a film is queued/running the UI shows a status banner + node status line and polls `getFilmStatus` every 4s; when the background task saves the film, the project is refetched and the film simply appears on the 成片 node (inline player + download) and in 生成历史. Failed status shows the stored error with a 重新生成 button.
- **`requestFilm` action** (projectId, optional packageNodeId): returns the existing queued/running request if one is active (<3h old; older is auto-failed as timed out). Otherwise it collects shots server-side from the saved graph JSON — package node's wired images in edge order, else all canvas images in reading order (y, then x) — using ALL shots with no batching (the background task itself works in consecutive rounds of ≤6 clips, so no user-side batching is ever needed): 0 shots → error; any selected shot without an image (no blobKey) → error listing its titles; >24 shots → error asking to split into two 成片 nodes. The cap was raised 12 → 24 after the audit caught that the user's own project 《我的第一个短片》 has 13 shots wired into its 成片 node and was being blocked outright — the user must never have to delete storyboards to make a film. It inserts a `film_requests` row (migration `0003_add_film_requests`: project_id, package_node_id, status, shots_json with blobKeys — never URLs — shot_count, film_blob_key, error, timestamps), then `ctx.agent.spawnTask` with `expectsAction: "saveFilmToProject"` and `dedupeKey: film-<projectId>-<requestId>`, plus a best-effort guarded `ctx.notifyParent` heads-up when the runtime exposes it. The assignment tells the spawned Muse: read shots via `getFilmRequest`; storyboard image bytes are NOT readable from chat (ctx.blobs has no read API — same limitation recorded for the first film), so regenerate each shot's keyframe from its image_prompt; generate ONE true-motion clip per shot from keyframe + motion_prompt + camera_motion (max 6 clips per round, consecutive rounds past 6); edit in index order with ffmpeg burning each caption; save via `saveFilmToProject`; report in chat; never fake a film.
- **`getFilmRequest` action** (requestId): returns the stored shot list (index, node_id, title, blob_key, image_prompt incl. upstream text + style suffix, motion_prompt, caption, duration_seconds, camera_motion label, aspect) + project name; flips queued → running.
- **`getFilmStatus` action** (projectId): latest request's status/request_id/shot_count/error/created_at + film_url resolved from the stored blob key when done.
- **`saveFilmToProject` action** (projectId, optional packageNodeId, optional requestId, videoBase64, mime video/mp4): stores the MP4 at `p<id>/film-<ts>.mp4` in ctx.blobs, inserts a `generations` row (kind video, prompt `成片：<项目名>`), patches the saved graph JSON — url/blobKey onto the given package node, else the first video node, else a newly created 成片 node wired from all image nodes — and marks the film request done with the film blob key.
- **Kept**: `uploadAsset` manual upload on the 成片 node as a fallback （手动上传视频）, inline playback and download of the saved film. Video nodes are labelled 成片 (previously 分镜包）; existing saved graphs keep working since only labels/defaults changed.
- This supersedes the "Division of labor" section above wherever they conflict: the division of labor (tool storyboards, Muse generates true motion chat-side on Muse's token) is unchanged — only the hand-off is now automatic instead of a manual export.

### Stuck film detection + recovery (edit, 2026-11-10)
User: 「成片生成中：正在逐镜头生成真运动视频并按剧情剪辑 · 镜头进度 0/13 · 已用时 21 分 46 秒。是不是卡住了」 — yes, it was stuck: progress stayed 0/13 for 21m46s and the old code offered no diagnosis and no exit (active-request lock lasted 3 hours, no cancel action, `getFilmStatus` didn't even expose `updated_at`).
- **Root cause**: the background task died / never reported without the row ever leaving `running`; `requestFilm` returned the dead request as `already` for up to 3h; the UI had no staleness signal and no cancel path.
- **Server stall model** (`filmStallState` in actions.ts, based on `updated_at` which only moves on `reportFilmProgress`/status changes): WARN at 5 min without an update, AUTO-FAIL at 15 min without an update, HARD CAP auto-fail at 45 min total. `getFilmStatus` now returns `updated_at` + `is_stalled` and self-heals on read (a past-threshold running request is flipped to `failed` with a plain-language reason on the next poll — so the user's currently stuck 0/13 request resolves itself to the retry state as soon as the new build is opened). `requestFilm` uses the same stall check instead of the 3h rule, so a retry is never blocked by a corpse request.
- **New `cancelFilm` action** (projectId): marks the latest queued/running request `failed` with a user-ended message, freeing the project immediately. `saveFilmToProject` gained a supersede guard: a late save from a cancelled/auto-failed request that has been replaced by a newer request still lands in history but does not resurrect the dead row.
- **Heartbeat instruction**: the `requestFilm` assignment now requires the background task to report immediately at start, after each clip, and as a heartbeat (~every 3 min) during any long single clip — going 15 min silent is defined in the assignment as auto-fail.
- **Client**: banner + 成片 node + top-bar button all gain a stalled state (≥5 min without an update): red “可能卡住了” copy stating how long since the last update and total elapsed, plus 「结束并重新生成」 (cancel + fresh request in one click, bypassing the stale busy flag) and 「结束这次生成」 (cancel only). A subtle “结束这次生成” is also available during healthy generation, and the healthy banner shows “上次进度更新于 X 前”.

User: 「把整套流程在工具里面可以自动化实现也可以自己分流程调整，自动化实现就和 Agent 通道，一句话指令就能让 Agent 在后台把搭工作流、写剧本、分镜、生视频、配乐整条线跑完，直接返回成品一样」 — dual mode: the manual node workflow stays exactly as-is; a new top-bar entry「✦ Agent 一句话成片」adds the one-sentence automatic channel.

Honest subcopy: the tool builds the workflow; background Muse generates true-motion clips, music and editing on Muse's own token and saves the film back; the page itself never generates video. Max 12 shots, converged at the script stage and stated in the panel.
- **New table `agent_runs`** (migration `0005_add_agent_runs`): project_id, instruction, target_duration, aspect, style, mode (auto/step), status state machine `queued→scripting→assets→storyboarding→(awaiting_confirm)→filming→scoring→editing→saving→done/failed/cancelled`, progress_done/total/stage, package_node_id, film_request_id, music_mood, error, timestamps.
- **`startAgentProduction`** creates a NEW project (existing projects untouched) + a queued run; the client then calls **`buildAgentProduction`** which orchestrates server-side reusing the existing platform channels (`ctx.inference` structured plan — title/anchor/musicMood/shots with 景别/画面/动作/字幕/时长/运镜/画面提示词/运动提示词, shots clamped to 12 and durations scaled to the target; `ctx.tool.generate_media` for images): zoned canvas input text node （一句话创意） → script text node (full storyboard table incl. 配乐情绪） → asset-lock image node (1 generated character/scene reference image; consistency is TEXT anchoring — the unified anchor description is baked into every shot node's prompt text, and the UI copy says exactly that) → per-shot image nodes (prompt/motionPrompt/caption/duration/motion all filled; images generated one by one via `generateAgentShotImages`, graph + run progress saved after EACH shot; a failed shot is marked `status:error` on its node with a retry note and does not lose the others) → 成片 node wired in story order (asset node is NOT wired into the film node, so it never becomes a shot).
- **Film handoff**: all shots ready + auto mode → `spawnAgentFilm` inserts a film_requests row and spawns the background task with the EXPANDED brief — per-shot true-motion clips (≤6/round), story-order editing with burned captions, PLUS background music matched to the script's musicMood mixed into the final MP4 (no narration), saved via the existing `saveFilmToProject` (which now also flips the linked agent run to done). Step mode (or any failed shot images) parks in `awaiting_confirm`: banner + 成片 node offer「继续生成成片」/「重新生成分镜」; the user may edit anything on the canvas meanwhile, and **`continueAgentProduction`** re-collects shots from the CURRENT saved graph (missing images → back to awaiting_confirm with the titles listed). `next:"storyboard"` regenerates every shot image from current node prompts, then re-parks (step) or proceeds to film (auto).
- **Progress & protection**: stage labels 正在写剧本 / 正在定版资产 / 正在生成分镜图 / 正在生成镜头视频 / 正在配乐 / 正在按剧情剪辑合成 / 正在保存成片； the spawned task reports BOTH `reportFilmProgress` and the new **`reportAgentProgress`** (status + doneShots + stage, heartbeat ~3 min). `getAgentRunStatus` syncs the filming phase from the linked film request (stage text → scoring/editing/saving; film done/failed ends the run) and applies the same stall model as film requests (5 min warn in the banner, 15 min no-update auto-fail, 45 min hard cap) — except `awaiting_confirm`, which waits on the user and never stalls. **`cancelAgentRun`** cancels the run and any linked in-flight film request. The build call can outlast a single request's time limit; progress is persisted per shot server-side, and the client re-checks the real run status before reporting a build failure.

The continue-to-film path was not sandbox-invoked (it spawns a real background task).

### Backspace safety + live film progress (edit, 2026-11-10)
User: 「backspace键不要删除当前节点，有可能需要移除单个文字，还要动态显示进度」
- **Backspace never deletes**: the global keydown handler used to treat `Delete` and `Backspace` identically, and its typing detection only checked `document.activeElement`'s tag — so Backspace could wipe the selected node when the user meant to remove one character. Now Backspace returns immediately at the window level (text fields handle it natively, one character at a time), deletion is `Delete`-only, and editable detection checks the event target AND the focused element across INPUT/TEXTAREA/SELECT/contentEditable. Help panel documents it: 「Backspace 只删文字，不删节点」.
- **Real dynamic progress**: `film_requests` gains `progress_done` + `progress_stage` (migration `0004_add_film_progress`). New `reportFilmProgress` action (requestId, doneShots, stage): monotonic, clamped to shot_count, ignored once done/failed. The `requestFilm` assignment now instructs the background task to report after EACH finished shot clip （正在生成镜头片段）, before editing （正在按剧情剪辑合成）, and before saving （正在保存成片）; `saveFilmToProject` completes the count/stage. `getFilmStatus` returns `progress_done`/`progress_stage` (done ⇒ progress_done = shot_count). The page polls every 4s while busy and renders: top banner + 成片 node determinate progress bar (done/total · %) once reports arrive, an animated indeterminate bar before the first report, the current stage label, a per-second ticking elapsed timer (from `created_at`), and a `生成中 X/N` top-bar button. No simulated percentages — the bar only ever shows counts the background task actually reported.

### Node images never updating: stale-graph overwrite + gated reloads (edit, 2026-11-10)
User: 「节点图片进度没有更新」 (with screenshot: agent banner at 8/8 editing, but shot nodes 5–8 blank on the canvas and in the 成片 node's shot list).
- **Diagnosis (from the captured evidence DB)**: the server build worked — `generations` held all 8 shot images for the project and the film request's `shots_json` collected all 8 blobKeys from the stored graph. But the STORED graph itself only had images on shots 1–4: after the build, a page-side save of a stale local graph (which had only ever loaded shots 1–4) overwrote the server's complete graph, wiping shots 5–8 from the nodes permanently.
- **Why the page was stale**: the progress-reload effect only fired while the run was scripting/assets/storyboarding and keyed on `status|done|stage`; the storyboarding→filming transition (when the final shots land) triggered no reload, and a reload whose refetch joined an in-flight pre-write request was never retried. **Why the stale copy won**: the canvas autosaves the whole local graph on any change (a pan/zoom is enough) with no regard for server-side generation in flight, and `saveProject` replaced the stored graph wholesale. Server-side, `generateAgentShotImages` also threaded a pre-loop snapshot of the project row, so its writes were based on increasingly old state.
- **Fix — client**: (1) the agent reload effect now keys on `projectId|status|done|total|stage|updated_at` and fires in EVERY live phase plus `awaiting_confirm` and `done` (only none/failed/cancelled are excluded), with a second delayed invalidation 1.5s later to beat the in-flight-refetch race; (2) autosave (`doSave` + the debounce effect) is paused while the agent build owns the canvas (`agentBuilding`), resuming automatically when the build parks or hands off to filming.
- **Fix — server**: (1) `saveProject` runs `preserveStoredMedia`: a node present in both graphs whose stored copy has media (url/blobKey) and whose incoming copy has none keeps the stored media — generated media can no longer be erased by a save that doesn't know about it; node deletions and media replacements are unaffected. (2) During an active build (latest agent run in scripting/assets/storyboarding), `saveProject` accepts the rename but keeps the server's graph (backstop for the pre-first-poll race and direct flush calls). (3) `generateAgentShotImages` re-reads the project row at the top of every iteration and again before writing, patching ONLY the current shot's node into the freshest stored graph. (4) `getProject` self-heals in the response only: image/video nodes with no media are backfilled from the project's own generation history (latest row per nodeId, URL freshly resolved via `ctx.blobs.getUrl`) — this restores the already-wiped shots 5–8 of the affected project on next open without rewriting stored rows; the client's next normal save persists the healed graph, and rule (1) keeps it from regressing.

### "正在打开画布…" overlay never clears (edit, 2026-11-10)
User: 「一直是正在打开画布，这个是个bug」 (screenshot + captured evidence: the canvas is fully rendered — every node and image present, network idle, no console errors — yet the translucent 正在打开画布… overlay sits on top of it, during the filming phase of project 《碟中喵：绝密垂降》 at 4/7).

### Structural fix: whole-file save abolished, chunked verified save (edit, 2026-11-10)
User: 「工具每次到了最后都会卡住，分析原因，以及彻底解决」 — with a verified five-run evidence chain from one day, ALL failing at the same final step while every earlier stage (script, asset lock, storyboard images, clips, edit, music) never failed once: request 1 stored byte-mangled yet marked done; request 2 rendered then hung in 正在保存成片 forever; project 3 re-encoded 6+ shrinking versions over 8+ silent minutes retrying the same all-or-nothing call; project 5's film arrived as a 4,290-byte truncated prefix even at small size (proving it was never a size problem); request 7 (after the integrity gate) reported 正在保存成片（第 1 次尝试）at 17:42 and the task vanished — no second attempt, no failFilmSave, nothing landed until a status query auto-failed it at the 45-min cap hours later. **Single point of failure: the finished film crossed as ONE base64 action argument — all-or-nothing, non-resumable, and if the call hangs or dies with the agent's turn, every remedy written into later code never executes.**
- **Previous "chunked upload impossible" conclusion — overturned**: the earlier reasoning was that ctx.blobs cannot READ bytes back, so the server could never reassemble chunks into one playable file. That is still true server-side, but reassembly never needed to be server-side: the BROWSER can fetch chunk blob URLs and reassemble. Verified against the shipped SDK: `BlobClient` = put/getUrl/head/delete/list (`head` returns sizeBytes — a real byte-level fact the server CAN check), and `crypto.subtle` is available in actions for server-side hashing.
- **New save path (migration `0006_add_film_assemblies_chunked_save`: `film_assemblies` + `film_chunks`)**, shared by the plain pipeline (`requestFilm` brief) and the Agent pipeline (`spawnAgentFilm` brief); `saveFilmToProject` is DELETED and both spawn briefs now end at `finalizeFilmSave` (`expectsAction` updated):
  1. `beginFilmSave(requestId, chunkCount, totalBytes, sha256, mime)` registers the manifest and returns the indices ALREADY received — an interrupted save resumes, never restarts; a manifest that disagrees with a previously registered one is rejected outright.
  2. `saveFilmChunk(requestId, index, dataBase64 ≤32KB raw, sha256)` — the server decodes, computes SHA-256 over the bytes it ACTUALLY received and compares with the declared hash BEFORE storing: a mangled chunk is rejected on the spot and only that chunk is resent (this is the per-chunk form of the integrity gate — the full box walk moved client-side, see below, because the server still cannot read chunks back to walk them). Chunk 0 additionally passes a structural head gate: it must open with a valid `ftyp` box (sane size + printable major brand), so a hash-self-consistent non-MP4 can never enter storage — verified in sandbox both ways (150 zero bytes rejected at chunk 0; a real MP4 head accepted). Re-sending a stored chunk byte-identically is a no-op success; sealed assemblies are immutable. Every stored chunk reports progress server-side (`正在保存成片 · 已传 X/N 片` on the film request AND any linked agent run) and bumps `updated_at` — saving now produces its own heartbeat.
  3. `finalizeFilmSave(requestId)` seals only when every chunk 0..N-1 is present, each stored blob's `head().sizeBytes` equals its recorded length, and lengths sum to the registered total; only then does it patch the 成片 node (new `filmAssembly` manifest field on the node; url/blobKey cleared), insert the history row (blob_key = marker `film-assembly:<requestId>`), seal the assembly, and flip request + linked agent run to done via the shared `completeFilmRequest` (same supersede guard as before). Missing chunks are refused with the exact missing indices.

Any failure shows a plain error and NO download. Assembly-verification failure on the node propagates to the banner (same broken-film pattern as legacy saves), so banner/node/history can never contradict each other. Assemblies are cached per request so node/banner/history share one fetch.
- **Stall model retuned to the chunk rhythm**: the saving stage no longer gets lenient thresholds (was 10 min warn / 30 min auto-fail) — every chunk is a report, so saving uses the same 5/15 min as every other stage and the 45-min hard cap stays; a task that dies mid-save now auto-fails within 15 min of silence instead of hanging to the cap (request 7's failure mode). Client mirrors updated to match (5 min warn everywhere; copy now says 分片上传，每存好一片都会报一次进度）.
- **Not regressed**: per-chunk ingest hashing + chunk-0 ftyp gate + whole-file length/SHA/structure verification is strictly stronger than the old single box walk; media-preservation merge and history backfill now understand `filmAssembly` (backfill skips marker keys); the canvas loading fix, Backspace safety, and the damaged-label handling for the two already-corrupt legacy films are untouched (legacy single-blob films still play/download exactly as before; `uploadAsset` manual upload unchanged).

### Addendum (same edit): bytes no longer travel through the agent at all
